# Fable 작업 지시서 — 프리스크리닝 엔진의 미검증 구간 측정·개선

아래 전체를 Fable 세션에 그대로 붙여넣는다. 레포는
`claude/dcamp-screening-engine-test-ngk7ly` 브랜치를 쓴다.

---

## 목표 (한 줄)

이 엔진에서 **한 번도 측정되지 않은 구간** — `사실 → 레벨(L1~L5) 분류` — 의
재현성을 독립적으로 측정하고, 불일치가 나온 지점의 레벨 정의를 그 근거로만 날카롭게
만들어라. 합불 라벨에 규칙을 맞추는 작업은 **하지 마라.**

## 왜 이것인가

엔진의 핵심 설계 주장은 "같은 사실을 넣으면 같은 점수가 나온다"이다. 이 주장은
두 구간으로 나뉜다.

| 구간 | 검증 상태 |
|---|---|
| 레벨 → 가중평균 → Tier | ✅ 코드로 강제, 테스트 54건 통과 |
| **사실 → 레벨 분류** | ❌ **한 번도 측정 안 됨** |

두 번째 구간은 Claude(Opus)가 **혼자, 한 번** 판단한 결과다. 독립 평가자와의 일치율이
낮으면 지금 리포트의 모든 수치(확정 판정 정확도 100%, 합격사 오탈락 0개사 등)는
분류자 한 명의 취향일 뿐이다. 이 측정은 **다른 모델만 할 수 있다.** 그래서 이 작업이
가장 큰 변화를 만든다.

## 지금 상태 (이미 측정된 것 — 다시 하지 마라)

라벨 표본 10개사(합격 8 + 확정 불합격 2), 전 기업 공개 정보만 사용(덱·CV·설문 없음).

| 버전 | 확정 판정 | 커버리지 | 확정 판정 정확도 | 틀린 단정 |
|---|---|---|---|---|
| v2 | 6/10 | 60% | 83% | SaaSMetrics(추천) |
| v3 | 2/10 | 20% | 100% | 없음 |

- SaaSMetrics = 500 Startups 실제 탈락 기업(창업자 공개). 지원 시점 유료 고객 수십 곳
  + 30% MoM. v2 는 B 추천으로 통과시켰고, v3 는 구간 [2.90, 4.10]이 추천선을 걸쳐 유보.
- 구간 폭의 **89%** 가 `확인 필요` 축에서 발생. 자료 완비 가정 시 확정 판정 2/10 → 9/10.
- 추천선 민감도: 3.00~3.50 에서 정확도 100% (3.25 는 우연이 아님).
- LOO 교차검증: 단정 4/10, 정확도 75% — 작은 표본에서 컷오프를 고르면 SaaSMetrics
  홀드아웃 시 2.75 가 선택돼 오탐이 재발한다.
- **합격 4개사 중 3개사는 in-sample** (규칙을 그들의 실패를 보고 만들었다).
  `backtest.RESCUED_BY` 에 어느 수정이 어느 기업을 구제했는지 기록돼 있다.
- 확정 불합격은 **2개사뿐**. 정밀도·특이도는 통계적으로 추정 불가.

## 절대 금지 (이걸 어기면 작업 전체가 무의미해진다)

1. **`WEIGHTS` 를 바꾸지 마라.** 디캠프 내부 루브릭이다. `test_weights_unchanged` 가 막는다.
2. **합불 라벨을 보고 컷오프·레벨표를 조정하지 마라.** 표본 10개사다. 조정하면 암기다.
   LOO 실험이 그 위험을 이미 실측했다(위 참조).
3. **작업 1을 끝내기 전에 `dataset.LEVELS_V2` / `Company.levels` / `dataset.FIT` /
   `ground_truth` 를 읽지 마라.** 읽으면 블라인드 측정이 오염되고 이 작업의 유일한
   가치가 사라진다. 읽지 않았다는 것을 산출물에 명시하라.
4. **기존 테스트 54건을 통과 상태로 유지하라.** 특히
   `test_v3_catches_the_v2_false_positive`, `test_v2_does_not_reject_actual_admits`,
   `test_confident_decisions_have_no_error`, `test_unknown_axis_is_not_a_penalty`,
   `test_no_version_is_perfect`, `test_agreement_signal_is_documented_as_failed`.
   이들을 수정해서 통과시키는 것은 회귀다 — 실패하면 원인을 보고하라.
5. **없는 사실을 만들지 마라.** 근거가 없으면 `확인 필요`(None)다. 정보 부재를 L1 이나
   중간값 L3 으로 채우는 것이 v1 의 최대 결함이었다.

## 작업 1 — 블라인드 재분류 (이 지시서의 핵심)

### 1-1. 블라인드 입력 생성

`screening/blind_fixture.py` 를 만들어, `dataset.COMPANIES` 에서 **다음만** 추출해
`output/screening/blind_input.json` 으로 저장하라.

```
key, name, track, sector_key, sector_note, stage_band,
facts            (사실 문장 + 증거 등급 — 이것이 유일한 판단 근거)
product_note, priced_round, cap_table_note, english_note
```

`levels`, `LEVELS_V2`, `FIT`, `ground_truth`, `unstable`, `note`, `fit_reason`,
`sources`, `needs_confirm` 은 **절대 포함하지 마라**(`note` 에는 정답이 적혀 있다).

### 1-2. 독립 분류

`blind_input.json` 만 보고, `screening/ENGINE_V2.md` 의 §3(밴드별 레벨표)·§4(증거
등급 규칙)에 따라 각 기업의 4개 축을 직접 분류하라. 근거가 `문서 명시` 미달이면 `None`.

결과를 `screening/levels_fable.py` 에 다음 형태로 쓴다. 축별로 **근거 문장을 반드시
남겨라** — 나중에 불일치 원인을 추적하는 데 이것만 쓴다.

```python
LEVELS_FABLE: dict[str, dict[str, tuple[int | None, str]]] = {
    "cardmonster": {
        "traction": (3, "근거: ..."),
        ...
    },
}
CONFIDENCE: dict[str, dict[str, str]] = {   # 축별 "high" | "low"
    "cardmonster": {"traction": "low", ...},
}
```

`CONFIDENCE` 는 그 축을 정하면서 **다른 레벨과 진짜로 헷갈렸는지**를 기록한다.
작업 2에서 "불일치가 예측 가능했는가"를 검증하는 데 쓴다.

### 1-3. 일치율 측정

`screening/agreement.py` 를 만들어 다음을 계산·출력하라. 이때 처음으로
`dataset.LEVELS_V2` 를 읽는다.

- **완전 일치율** — 레벨이 정확히 같은 축의 비율 (None 도 값으로 취급)
- **인접 일치율** — ±1 레벨까지 같다고 보는 비율
- **None 일치율** — `확인 필요` 판단 자체가 일치하는 비율 (증거 등급 규칙의 재현성)
- **Cohen's κ** — 우연 일치를 제거한 값. 외부 라이브러리 없이 직접 구현하라
  (numpy/scipy 없이 순수 파이썬. 이 레포는 의존성이 `requirements.txt` 뿐이다)
- **축별 일치율** — Traction/TRL, Team, Market/양산, Moat/고객 각각
- **불일치가 Tier·구역을 바꾸는가** — 두 분류를 각각 `rules_v2.aggregate` 와
  `rules_v3.decide` 에 넣어 Tier·구역이 달라지는 기업을 나열

## 작업 2 — 불일치 분석 → 레벨 정의 개선

### 2-1. 판단 규칙 (이대로 따르라)

| 인접 일치율 | 해석 | 해야 할 일 |
|---|---|---|
| ≥ 85% | 분류가 재현된다 | 개선 여지 작음 — 결과만 보고 |
| 70~85% | 특정 축이 흔들린다 | 해당 축의 레벨 정의만 개선 (2-2) |
| < 70% | **집계 규칙 개선은 무의미했다** | 레벨 정의 전면 재작성 (2-2) + 지금까지의 정확도 수치가 왜 신뢰 불가인지 명시 |

`None` 일치율이 낮으면(< 80%) 원인은 §4 증거 등급 규칙의 모호함이다. 그것을 먼저 고쳐라.

### 2-2. 개선 방법 (근거 있는 것만)

불일치한 축 각각에 대해, 두 분류의 **근거 문장을 나란히 놓고** 무엇이 갈렸는지 특정하라.
갈림 유형은 대개 다음 중 하나다:

- 같은 사실을 다른 레벨로 읽음 → **레벨 경계에 판별 질문을 추가**
  (예: "외부 사용자 존재"와 "유료 고객 1곳"을 가르는 질문: *돈이 실제로 이동했는가?*)
- 한쪽은 사실로 인정, 다른 쪽은 `확인 필요` → **증거 등급 판정 예시를 추가**
- 축 자체의 해석이 다름 (예: 로봇 안전 SW 의 Moat 를 인증으로 볼지 SW 로 볼지)
  → **섹터별 적용 노트를 추가**

개선은 `screening/ENGINE_V2.md` §3·§4 에 **판별 질문과 실제 예시**를 추가하는 형태로
한다. 추상적인 문장을 더 쓰지 마라. 각 판별 질문에는 이번 20개사에서 나온 실제 사례를
붙여라.

**금지**: 불일치를 줄이려고 레벨 개수를 줄이거나, "애매하면 L3" 같은 규칙을 넣는 것.
그건 v1 의 중간값 함정을 되살리는 것이다.

### 2-3. 개선 효과 측정

개선한 정의로 **불일치했던 축만** 다시 분류하고(일치했던 축은 건드리지 마라),
인접 일치율이 얼마나 올랐는지 보고하라. 오르지 않았다면 그 개선은 실패다 — 되돌리고
그렇게 기록하라.

## 작업 3 — 재측정

`python -m screening.backtest --report` 와 `python -m screening.experiment --report`
를 두 분류(Claude / Fable)로 각각 돌려 다음을 비교하라.

- 확정 판정 정확도·커버리지 (v2, v3)
- 합격 8개사 중 비추천으로 떨어진 기업 수
- SaaSMetrics 판정 — 어느 분류에서도 `확정 추천`이 나오면 안 된다

**결론이 분류자에 따라 바뀌는지**가 핵심 질문이다. 바뀐다면 그 사실이 이 작업의
가장 중요한 산출물이다. 좋게 보이도록 쓰지 마라.

## 작업 4 (선택, 여력 있으면) — 음성 표본 확대

확정 불합격이 2개사뿐이라 오탐률의 참값을 모른다. 창업자가 스스로 공개한 탈락 사례를
더 찾아라. 검색어 예: `"rejected by 500 Startups"`, `"didn't get into HAX"`,
`액셀러레이터 탈락 후기`, YC/Techstars 탈락 후 회고 글. 조건:

- **지원 시점의 트랙션·팀·제품 상태가 글에 적혀 있어야 한다** (없으면 분류 불가 → 제외)
- 어느 프로그램에 언제 탈락했는지 명시 → `ground_truth="rejected_500"` 등으로 라벨
- 후행 정보(탈락 후 성공/실패)는 `[후행]` 표시하고 레벨 분류에서 제외

3개사 이상 추가되면 특이도를 처음으로 추정할 수 있다. 추가 못 했으면 "찾지 못했다"로
기록하라 — 없는 것을 만들지 마라.

## 산출물

| 파일 | 내용 |
|---|---|
| `screening/blind_fixture.py` | 블라인드 입력 생성기 |
| `screening/levels_fable.py` | Fable 독립 분류 + 축별 근거 + CONFIDENCE |
| `screening/agreement.py` | 일치율·κ·축별 분석·Tier 영향 계산 |
| `screening/AGREEMENT.md` | 측정 결과 리포트 (생성물) |
| `screening/ENGINE_V2.md` | §3·§4 에 판별 질문·예시 추가 (개선분) |
| `test_screening_offline.py` | 신규 테스트 추가 (기존 54건 유지) |

`AGREEMENT.md` 에 반드시 포함할 것:

1. 완전/인접/None 일치율, κ, 축별 일치율
2. Tier 또는 v3 구역이 달라진 기업 목록 — 기업명과 갈린 축까지
3. 불일치 사례별 두 근거 문장 대조표
4. `CONFIDENCE="low"` 로 표시한 축이 실제 불일치와 얼마나 겹쳤는가
   (겹치면 엔진이 자기 불확실성을 스스로 안다는 뜻 → `unstable` 자동 생성에 쓸 수 있다)
5. 개선 전후 일치율
6. **작업 1-2 를 끝낼 때까지 Claude 의 분류를 보지 않았다는 확인 문장**
7. 결론이 분류자에 따라 바뀌는지 — 바뀌면 그대로 쓸 것

## 신규 테스트 (최소 3건)

- 블라인드 입력에 정답·기존 분류가 새어들지 않는지 (`blind_input.json` 에
  `ground_truth`/`levels`/`note` 키가 없음을 단정)
- κ 계산의 정확성 (완전 일치 → κ=1.0, 무작위 수준 → κ≈0 인 인공 입력으로)
- 두 분류 모두에서 합격사가 `확정 비추천`으로 떨어지지 않는지

## 합격 기준

1. 기존 테스트 54건 + 신규 테스트 전부 통과
2. `AGREEMENT.md` 에 위 7개 항목이 수치와 함께 존재
3. `WEIGHTS` 불변, 컷오프가 라벨 기준으로 조정되지 않았음
4. 개선한 레벨 정의가 실제로 일치율을 올렸다는 측정치(작업 2-3). 못 올렸으면
   실패로 기록되어 있을 것
5. 커밋 메시지에 일치율·κ 수치 포함

## 이미 빠졌던 함정 (반복하지 마라)

1. **버전 합의를 신뢰도 신호로 쓰기** — 시도했고 실패했다. v1 neutral 과 v2 가
   SaaSMetrics 를 둘 다 추천한다. `backtest.agreement()` 에 실패로 기록돼 있다.
   같은 것을 다시 만들지 마라.
2. **라벨 6~10개로 컷오프 튜닝** — LOO 가 위험을 실측했다(정확도 75%로 하락).
3. **정보 부재를 중간값으로 메우기** — Market 축을 모르는데 "크지만 논증이 약함"(L3)
   으로 채우면 모르는 것이 판정에 섞인다. v1 의 최대 결함이었다.
4. **재현율만 올리기** — v1→v2 에서 합격사 오탈락은 0이 됐지만 SaaSMetrics 오탐이
   생겼다. 한쪽 지표만 개선하면 다른 쪽이 깎인다. 두 지표를 항상 같이 보고하라.
5. **"완성됐다"고 쓰기** — 확정 불합격 2개사로는 정밀도를 주장할 수 없다.
   측정한 것과 측정 못 한 것을 항상 분리해 쓰라.
