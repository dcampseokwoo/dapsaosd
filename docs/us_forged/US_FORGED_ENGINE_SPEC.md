# US FORGED 후보 선별 엔진 — 개선 작업 지시서

**대상 프로그램:** 디캠프 x HAX Hardtech Pre-Program "US FORGED"
**작성 근거:** 엔진 출력물(338개사)을 원본 DB 3,424행 전수와 대조한 감사 결과
**작업 원칙:** 섹션 0을 먼저 읽고, 수정 계획을 보고한 뒤 승인받고 진행할 것. 코드부터 치지 말 것.

---

## 0. 이 엔진의 목적을 다시 정의한다

이 엔진은 **"요건을 충족하는 기업을 선발"하지 않는다.** 그건 이 DB로는 불가능하다.

공고의 핵심 요건 4개 중 3개는 GBD DB에 **컬럼 자체가 존재하지 않는다.**

| 공고 요건 | DB로 검증 가능? | 현재 커버리지 |
|---|---|---|
| Pre-Seed~Seed 단계 | 부분 가능 | `투자 스테이지` — 단, 620곳이 "알 수 없음" |
| 미국 진출 의지 | 사실상 불가 | `타겟 국가` — 3,371곳 결측 (98.4%) |
| Lab-scale 이상 프로토타입 | **불가** | 컬럼 없음 |
| 창업자·CTO 기술 전문성, 기술 차별성·특허 | **불가** | 컬럼 없음 |

따라서 엔진의 목적은 정확히 이것이다.

> **DB에서 명백히 부적합한 기업을 배제하고, 남은 기업을 설문 발송 우선순위대로 정렬한다.**

이 정의에 맞춰 전체 코드베이스를 정리할 것.

- `selected`, `qualified`, `passed`, `합격` 같은 식별자를 `shortlisted`, `outreach_candidate`로 변경
- 출력물 어디에도 "요건 충족" / "선발" 로 읽히는 문구를 남기지 말 것
- 모든 통과 판정에는 "무엇을 검증하지 못했는지"가 함께 출력되어야 함 (섹션 6)

## 1. [P0] 업종 라벨 화이트리스트를 폐기하고, 사업 소개문 기반 분류로 전환한다

### 현상

엔진은 `업종(CB 기준)` 컬럼을 영문 화이트리스트와 문자열 매칭해서 하드테크 여부를 판정하고 있다. **이것이 모든 결함의 뿌리다.**

### 근거 (실측)

**(a) 라벨 표기가 DB 내부에서 일관되지 않다.**

대부분은 영문 크런치베이스 라벨이지만, 일부 행은 한글 레거시 라벨(`소재/부품/장비`, `기후테크`, `IT서비스/솔루션`, `컨텐츠/소비재`, `바이오/헬스케어`)로 입력되어 있다.

- 초기단계 기업 중 한글 라벨 보유 **31곳 → 통과 0곳 (통과율 0%)**
- 그중 `소재/부품/장비` 7곳, `기후테크` 1곳 — **공고 핵심 모집 분야가 표기 방식 하나 때문에 전멸했다**
- 실제 탈락 사례: 휴젝트(에너지 하베스팅), 비즈(소형모듈원자로 SMR), 위드로봇(산업용 모니터링 로봇), 자이스웍스(설비 제어), 레디로버스트머신(에너지 회수 시스템) — 전부 `소재/부품/장비` 라벨

**(b) 라벨이 사업의 실체를 담지 못한다.**

- 업종 `Space` 인 초기단계 1곳 → 통과 0곳. 그 1곳이 **무인탐사연구소**(달 탐사 로버, "국내 유일 우주 로보틱스 기업", Seed)다. 공고의 Aerospace 분야에 정면으로 부합하는데 탈락했다.
- 업종 `Semiconductor` 인 초기단계 2곳 → 통과 0곳. 그중 하나가 **코리아 인스트루먼트**(반도체 웨이퍼 테스트용 프로브카드 제조)다.
- 반대로 라벨이 `Manufacturing`이면 화장품 제조사와 반도체 장비사가 똑같이 통과한다.
- 라벨에 `Audio`가 있다는 이유로 **(주)신성사운드모션**(MEMS 가속도·자이로 센서 설계, MEMS 마이크로폰)이 소비재로 탈락했다.

### 요구사항

1. **`1줄 사업 소개` 컬럼을 1차 판정 근거로 삼는다.** DB 3,424행 중 3,423행이 채워져 있어 커버리지 문제가 없다.
2. `업종(CB 기준)`과 `기술` 컬럼은 **보조 신호로만** 사용한다. 단독 탈락 사유로 쓰지 않는다.
3. 정규식·키워드 매칭이 아니라 **LLM 분류**로 판정하되, 아래 스키마로 구조화 출력을 강제한다.

```json
{
  "company": "string",
  "verdict": "hardtech | software_only | consumer | not_a_startup | unclear",
  "matched_program_field": "Robotics/Automation | Advanced Manufacturing | Energy/Climate Tech | Industrial Hardware | Semiconductor/Advanced Materials | Sensor/Edge Device | Physical AI | Healthtech Device | Manufacturing Process Innovation | Aerospace | Quantum | Other Deeptech | None",
  "physical_product": true,
  "evidence": "판정 근거가 된 소개문 구절 원문 인용",
  "confidence": "high | medium | low"
}
```

4. **판정 기준을 프롬프트에 명시한다:**

> 이 기업이 **물리적 하드웨어·소재·장비·디바이스를 직접 설계하거나 제조하는가?**
> 소프트웨어로 하드웨어를 제어·최적화·분석만 하는 기업은 `software_only`다.
>
> - 반도체 팹 엔지니어를 대체하는 AI 에이전트 → `software_only` (업종 라벨이 Semiconductor여도)
> - 반도체 웨이퍼 테스트용 프로브카드 제조 → `hardtech`
> - 태양광 발전소 금융·시공 중개 플랫폼 → `software_only`
> - MEMS 마이크로폰 설계·제조 → `hardtech` (업종 라벨이 Audio여도)

5. `confidence: low`는 자동 탈락시키지 말고 **별도 버킷**으로 분리해 사람이 검토하게 한다.
6. 판정 결과를 캐시한다(사업자번호 키). 재실행 때 3,424건을 다시 호출하지 않도록.

## 2. [P0] 중복 엔티티를 정규화한다 — 스테이지 필터 누수의 진짜 원인

### 현상

현재 출력물에 **Series C 기업(`한국공장지붕태양광지주`)이 1곳 통과**해 있다. 요건은 Pre-Seed~Seed인데 필터가 뚫렸다.

### 근거

원인은 필터 로직이 아니라 **DB의 중복 엔티티**다. 신규 스냅샷 기준:

- **동일 사명이 2행 이상인 케이스 21건 (총 43행)**
- 중복 행끼리 **스테이지와 업종이 서로 다르다**

| 사명 | 행 A | 행 B |
|---|---|---|
| 한국공장지붕태양광지주 | `727-81-02043` / Sustainability / **Series C** | `597-88-01495` / Sustainability;Financial Services / **알 수 없음** |
| 딥메트릭스 | 사업자번호 결측 / **Series A** | `855-88-01407` / **Seed** |
| 알피 | `515-81-40648` / Hardware;Manufacturing / **Pre-IPO** | `821-86-02087` / Healthcare / **Pre-A** |
| 아폴론 | `661-81-02253` / Bio,Healthcare,Hardware / Pre-A | `667-81-02253` / Healthcare / Pre-A |
| 오믈렛 | 3행 존재, 스테이지 Seed / Pre-A / Pre-A |

엔진이 사명으로 dedup하면서 "알 수 없음" 행을 집어 통과시킨 것으로 보인다.

- 사업자번호 자체도 중복 39건, 표기 오류 존재 (`725-870-2428` — 하이픈 위치 오류, 앞뒤 공백 포함 값)

### 요구사항

- 사업자번호를 정규화한다: 공백 제거, `\d{3}-\d{2}-\d{5}` 패턴 검증, 미일치 값은 경고와 함께 별도 리포트
- 중복 엔티티 병합 규칙을 명시적으로 정한다. **권장: 보수적 병합** — 스테이지가 충돌하면 **더 후기 단계를 채택**한다(과선정보다 누락이 낫다는 판단이 아니라, 스테이지 이탈 기업을 잘못 넣는 게 더 큰 사고이기 때문). 업종/소개문이 충돌하면 두 값을 모두 LLM 분류에 넣고 하나라도 hardtech면 통과시킨다.
- 병합된 엔티티는 `merged_from: [사업자번호…]` 로 추적 가능하게 남긴다
- 중복 21건 목록을 별도 시트로 출력해 DB 관리자에게 정정 요청할 수 있게 한다

## 3. [P0] 스테이지 필터를 재작성한다

### 요구사항

1. **DB에 존재하는 모든 스테이지 값을 명시적으로 매핑한다.** 미매칭 값이 나오면 조용히 탈락시키지 말고 **예외를 던진다.**

```
IN_SCOPE     : Pre-seed, Angel, Seed
UNKNOWN      : 알 수 없음, (결측)          → 통과시키되 별도 티어
EXCEPTION    : Pre-A                       → 섹션 3-3 규칙 적용
OUT_OF_SCOPE : Series A~E, Pre-B, Series C, Pre-IPO, IPO(*), M&A(*)
```

2. **`Pre-seed`와 `Angel`이 현재 처리되지 않고 있다.** 공고 요건이 "Pre-Seed~Seed"인데 DB의 `Pre-seed` 4곳이 통과하지 못했다. (해당 4곳은 실제로는 전부 SW/소비재라 최종 결과는 같지만, 로직에 구멍이 있다는 뜻이다.)

3. **Pre-A는 자동 탈락시키지 않는다.** 아래 조건을 모두 만족하면 `stage_exception` 버킷으로 분리해 사람이 판단하게 한다.

```
투자 스테이지 == "Pre-A"
AND 타겟 국가에 "미국" 포함
AND physical_product == true
```

실제 해당 사례:
- **메디띵스** — NIRS 방광 모니터링 웨어러블 디바이스, 타겟 국가 미국
- **아폴론** — 무채혈 연속혈당측정(CGM) 디바이스, 타겟 국가 미국

`타겟 국가`가 98.4% 결측인 DB에서 "미국"이 명시된 기업은 극소수다. 이 신호를 스테이지 필터로 날려버리는 건 비용이 크다.

4. **`리옵스` 케이스를 반드시 확인할 것.** 이전 스냅샷에서 Seed였고 타겟 국가가 미국이며 실리콘밸리 프로그램 참여 이력까지 있는 T1 최우선 후보였는데, 신규 스냅샷에서 **Pre-A로 변경**되어 자동 탈락한다. 위 예외 규칙이 이 케이스를 잡아내는지 테스트로 검증하라.

## 4. [P1] 배제 규칙을 강화한다

현재 "비스타트업 법인 제외"가 5곳만 잡아내고 있고 누수가 있다.

- **법인격 패턴 배제:** `투자목적회사`, `유한회사`, `\d+호\s`, `SPC`, `투자조합`, `지주` (단, `지주`는 사명 끝에 올 때만 — 오탐 주의)
- **해외 법인 배제:** `Co., Ltd.`, `Joint Stock Company`, `Inc.` 등 외국 법인격 + 소개문에 해외 소재 언급. 사업자번호가 `OC*` 형식이거나 `외국법인_*` 인 행도 여기 해당.
  - 현재 잔류 중: `Zhongxing Machinery International Co., Ltd.`(중국), `Lihua Eco-Packaging Co., Ltd.`(중국)
  - 단, 국내 법인의 영문명(`Rooy, Inc.` 등)과 구분할 것. 사업자번호 형식이 1차 판별 기준이다.
- **뷰티/화장품은 소개문에 "제조"가 있어도 배제한다.** 현재 잔류: 파인유얼뷰티, 에코디엠랩(주), (주)닥터스텍, 주식회사 마린테크노

## 5. [P0] 골든셋 회귀 테스트를 만든다

### 왜 필요한가

**이게 없어서 지난 수정이 회귀를 냈다.** 소비재 오분류를 걷어내려고 화이트리스트를 좁혔더니, 직전 버전에서 T1이던 **무인탐사연구소**가 통째로 탈락했다. 한쪽을 고치면 다른 쪽이 깨지는데 이를 감지할 장치가 없었다.

### 요구사항

- `tests/golden_set.yaml` (별도 제공된 파일을 그대로 사용) 을 fixture로 삼는다
- 골든셋은 **레이어별로 분리 검증**한다. 이게 중요하다 — 분야 판정과 스테이지 판정은 다른 층위이고, 스테이지 값은 DB 스냅샷마다 바뀌므로 섞어서 테스트하면 안 된다.
  - `classification_must_pass` — 분류기가 `hardtech`로 판정해야 하는 기업 (스테이지 무관)
  - `classification_must_fail` — 분류기가 `hardtech`가 아니라고 판정해야 하는 기업
  - `stage_rules` — 스테이지 필터 단독 검증
  - `end_to_end` — 최종 파이프라인 통과/탈락
- `pytest`로 구성하고, 실패 시 **어떤 규칙이 어떤 판정을 냈는지** 출력한다
- 골든셋이 하나라도 깨지면 커밋을 막는다 (pre-commit hook)
- 새 오류를 발견할 때마다 골든셋에 한 줄씩 추가한다 — 이 파일은 앞으로 계속 자산이 된다

## 6. [P1] 출력 스키마를 바꾼다

### 제거하거나 고칠 것

- **`유사 HAX 합격사`** — 338행에 47종뿐이고, 한 문자열이 100행에 그대로 반복된다. 분야 라벨에서 기계적으로 생성된 값이라 정보량이 사실상 0이다. **삭제하거나**, 소개문 임베딩 유사도로 실제 계산해서 **유사도 점수와 함께** 출력하라.
- **`설문/확인 항목`** — 2종류가 337행에 반복된다. 기업별로 실제 비어 있는 항목을 채워라.

### 추가할 것

| 컬럼 | 내용 |
|---|---|
| `judgment_evidence` | 통과 판정 근거가 된 소개문 구절 원문 |
| `matched_program_field` | 공고 11개 모집 분야 중 매칭된 것 |
| `confidence` | high / medium / low |
| `unverifiable_requirements` | 이 기업에 대해 DB로 검증 불가한 공고 요건 목록 |
| `contact_status` | `email` / `website_only` / `none` |
| `merged_from` | 중복 병합된 경우 원본 사업자번호들 |

### 연락처 문제

**현재 338곳 중 170곳(50.3%)이 대표자 이메일 결측이다.** 발송용 리스트인데 절반이 연락 불가다.

- 이메일 없는 기업은 별도 시트로 분리하고 `Website` 컬럼을 함께 실어라
- 요약 시트에 `발송 가능 / 연락처 확보 필요` 를 명시하라

### 요약 시트에 반드시 기록할 것

```
input_snapshot   : 파일명
input_sha256     : 해시
input_rows       : 3424
engine_commit    : git rev-parse HEAD
run_timestamp    : ISO8601
```

## 7. [P0] DB 스냅샷을 고정한다

### 현상 — 실측으로 확인됨

DB가 살아있는 구글 시트에서 export되는 구조라 **실행할 때마다 결과가 바뀐다.**

같은 `Ver 26_01` 라벨, 같은 3,424행, 같은 업데이트 로그(마지막 기록 2026.07.22)인데, **18시간 간격으로 뜬 두 export 사이에서 `투자 스테이지`가 652곳(19%) 달라졌다.**

| | 이전 export (08-18 00:40) | 신규 export (08-18 18:56) |
|---|---|---|
| SHA256 (앞 16자리) | `d797b0ac9aee1d3b` | `58941558719c663e` |
| Seed | 493 | **571** |
| 알 수 없음 | 620 | **568** |
| Series A | 582 | **567** |
| Pre-A | 356 | **376** |
| 스테이지 적격 합계 | 1,132 | **1,175** |

**영향:** 현재 후보 338곳 중 **44곳이 신규 DB에선 스테이지 이탈**(Series A 12, Pre-A 11, Series B 8, Series C 5, Pre-IPO 4, M&A 4), 반대로 **202곳이 신규 적격 전환**된다.

### 요구사항

- 입력 DB를 `data/snapshots/` 에 `GBD_DB_YYYYMMDD_HHMM.xlsx` 형식으로 보관하고, 실행 시 사용한 스냅샷을 로그에 남긴다
- **`diff` 모드를 추가한다:** 두 스냅샷을 받아 (1) 어떤 기업의 어떤 컬럼이 바뀌었는지, (2) 그 변경이 후보 리스트에 미치는 영향(신규 진입 / 이탈)을 출력
- 기준 스냅샷: **`GBD_DB_20260818_1856.xlsx` (최신)**. 이전 스냅샷은 diff 검증용으로만 사용
